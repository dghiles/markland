# Incident: 2026-09-26 v236 deploy outage (CPU burst exhaustion)

**Date:** 2026-09-26 (all times UTC)
**Duration:** ~16 minutes of user-visible impact, 16:29:20 → ~16:45
**Impact:** `markland.dev` (web and `/mcp`) timed out or answered slowly. Sentry
uptime failed 14 of 15 checks from 16:29:49 to 16:43:49. Fly's edge returned 503s.
No data loss.
**Trigger:** the CI auto-deploy of PR #81 (`61bf8e4`, release v236)
**Resolution:** rollback to the v235 image (release v237) at 16:44:30
**Fix-forward:** PR #90, release v238, deployed 2026-09-27 02:21 UTC at a quiet
moment. The balance reset to ~47 s and climbed steadily with no throttle; 29 of
30 post-deploy health checks passed (the miss was during the machine restart).
**Root-cause confidence:** demonstrated in a calibrated reproduction that models
Fly's burst budget; not replayed on Fly itself. See [Confidence](#confidence).

## Summary

Markland runs on one Fly `shared-cpu-1x` machine. A shared vCPU gets a baseline
of 6.25% of a core and can burst above it by spending a banked balance, capped at
500 CPU-seconds. Before the deploy the machine had nearly all 500 s banked. The
v236 machine update started a fresh VM with about 50 s, and every MCP client
reconnected at once. Each authenticated request on a legacy-shape token costs
about 1 CPU-second of Argon2id verification, run synchronously on the event loop.
About 80 requests arrived over roughly 81 s (proxy concurrency peaked at 45),
which drained the 50 s in about a minute. Fly then held the VM at its 6.25%
baseline. From there every request took over 16× longer, `/health` timed out,
and clients retried into the backlog.

At ~16:36 a restart kept the empty balance and changed nothing. The 16:44:30
rollback worked because it was another machine update, which granted another
~50 s after the reconnect storm had died down. v235 was not cheaper: it has the
same cost per request.

PR #81 (the MARKLAND-9 `ClientDisconnect` handler) and the drift in the
`python:3.12-slim` base image between the v235 and v236 builds were both ruled
out: v235, which has neither, collapses the same way in the calibrated
reproduction, and the base-image drift makes no runtime difference.

## Evidence

500 s cap and 0.5 is empty. The unit comes from the idle refill rate. The
balance rises ~5.7 units/s while the VM uses ~0.4% CPU, which matches
(6.25% − 0.4%) × 100. It also squares with the drain: 28 s of balance gone in
the 30 s to 16:29:30 is one saturated vCPU.
[Fly's docs](https://docs.fly.io/machines/cpu-performance/) list a 500 s max
and a 5 s initial balance. On this day both the v236 update and the v237
rollback started at ~5000 units, about **50 s**.

### Cost per request

- Measured in prod at ~1.0–1.1 CPU-s per authenticated request, the same on v235
  and v236. On v236 there were 28 `last_used_at` WAL commits against ~30 CPU-s.
- The operator's Claude Code MCP token and the bot token are both legacy shape
  (`mk_usr_` + 43 chars, no embedded token id). Prod has ~10 active user tokens
  plus some agent tokens.
- On a throttled VM, 1 CPU-s of work takes at least 16 s of wall time. That is
  longer than both Fly's 5 s `/health` timeout and httpx's 5 s default.

### Reproduction harness

The harness ran v235 and v236 code on the u3 and u4 bases in a prod-like
container (litestream to a file replica, dummy Sentry DSN, linux/amd64). Under a
saturating soak every cell hit 93% mean CPU and failed health probes at the 5 s
client timeout, whatever the code or base. Under the lighter run no cell failed.
The only difference between code versions was the one #81 intended: v236 logs no
`Exception in ASGI application` / `ClientDisconnect` tracebacks, where v235 logs
1015 per soak. An edge probe covering split bodies, chunked TE, `Expect:
100-continue`, pipelining, half-close, pre-body and mid-body aborts, and a
20-request burst behaved the same on both versions.

## Root cause

**A machine update throws away the banked CPU burst, and a reconnect storm of
expensive auth requests spends the ~50 s it grants in about a minute.**

1. **Per-request auth cost.** `service.auth.resolve_token` runs synchronously
   inside async middleware, so it blocks the event loop. Tokens without an
   embedded `token_id` (issued before `markland-9dm`) go through
   `_resolve_legacy`. It selects every non-revoked token and Argon2id-verifies
   each one until a match. The verify uses argon2-cffi `PasswordHasher`
   defaults: t=3, 64 MiB, p=4. The cost grows with the token's position in the
   scan, and a bearer that matches nothing pays for every row.
2. **Deploys reset the burst.** A Fly machine update starts the new VM with
   ~50 s of balance, whatever was banked before. Both the CI deploy and the
   rollback did this. Any other machine update should behave the same way; that
   is expected but was not observed. A restart keeps the current balance and
   does not refill it.
3. **Deploys cause a reconnect storm.** The update drops every connection, and
   every MCP client (Claude Code sessions, the bot) reconnects and
   re-authenticates at once. In the logs most of the burst comes from one client
   address, consistent with the operator's own parallel sessions.
4. **Throttling feeds on itself.** Once the balance is gone the VM runs at
   6.25%. Requests queue behind the blocked event loop and clients time out and
   retry. Abandoned requests still finish their auth scan, so each retry adds
   work.

About 80 requests × ~1 CPU-s is far more than 50 s plus a 6.25% baseline can
cover. The throttle lasted until the rollback, another machine update, granted
a fresh 50 s after traffic had subsided.

### Confidence

- **Observed directly:** the balance reset on update, the exhaustion, the
  throttle, the restart not resetting the balance, and the rollback resetting
  it (all in the metrics); the per-request CPU cost (measured); the reconnect
  burst (logs).
- **Demonstrated in a calibrated reproduction:** that this cost times this burst
  causes the drain and the outage. The fix-forward's gate harness models Fly's
  budget: it runs the container at a full CPU until ~48 CPU-s are spent, then at
  6.25%. It replays a prod-sized reconnect burst (45 clients, 80 requests over
  80 s, a legacy token, 60 s client timeouts with one retry).
  - v235: `/health` failed 10 s in, still at full CPU (like 16:29:20), and never
    recovered in 20 minutes.
  - The same burst with a new-shape token: 0 failures.
  - The fix-forward: ~5.7 prod-equivalent CPU-s, no throttle, 0 failures.
  The burst has not been replayed on a real `shared-cpu-1x`.

## What was ruled out

Neither was needed for the failure. v235, which has neither, collapses the
same way in the calibrated reproduction.

- **PR #81 (MARKLAND-9 `ClientDisconnect` handler).** The v235 → v236 source
  diff is 13 lines in `src/markland/web/app.py`, adding an exception handler
  on the MCP sub-app, plus tests. Prod cost per request is the same on v235 and
  v236. In the harness, v235 fails the same way as v236 under the same load, and
  the edge probe behaves the same on both. Reverting it would not have helped:
  the rollback "fixed" things only through its fresh burst balance.
- **Base-image drift (u3 → u4).** The unpinned `FROM python:3.12-slim` resolved
  to a different digest for v236 than for v235. The 2×2 matrix (code × base)
  shows no material difference between bases.

## Contributing factors

- **Legacy tokens still in use.** The O(N) Argon2 scan runs for every
  pre-`markland-9dm` token and for every bearer that fails to resolve. The
  operator's Claude Code token and the bot token are both legacy.
- **`resolve_token` is wired into two middlewares.** `RateLimitMiddleware`
  (outermost, `rate_limit_middleware.py:87`) resolves lazily, and
  `PrincipalMiddleware` (`principal_middleware.py:50`) resolves again. The
  investigation brief said every authenticated request resolves twice. A direct
  count on `61bf8e4` (live uvicorn, Sentry initialised as in prod, six token
  rows) shows otherwise. A valid legacy bearer made 1 `resolve_token` call and
  6 verifies, and an invalid bearer made 2 calls and 12 verifies. On a
  **successful** resolve, `RateLimitMiddleware` stores the
  principal on `request.state` and `PrincipalMiddleware` skips its own call:
  one scan. On a **failed** resolve (a revoked, stale or mistyped bearer, which
  ends in a 401) both run: two full scans, 2N verifies. Either way the work
  blocks the event loop.
- **CI reported success while prod died.** `--strategy immediate` returns once
  flyctl accepts the release, so the Deploy job was green at 16:28:22.
  `needs: []` meant the Test job could not block it, and Test finished green at
  16:30:28, after the fact. Nothing in CI looks at the machine after the deploy.
- **Every push to `main` deploys**, docs included (v235 itself was a docs-only
  push). Every deploy resets the burst balance, so even a docs push carries this
  risk until `paths-ignore` lands.
- **Unpinned base image.** Not causal, but it put a second variable into the
  v235 → v236 change and cost investigation time to rule out. A rebuild of the
  same commit is a different image.
- **The verification client made it worse.** The post-deploy check used
  httpx's 5 s default timeout against a VM where requests needed 16 s or more.
  Its requests were abandoned but still paid for, and a retry would have added
  more.
- **The restart looked like a fix but wasn't.** Restarting is the instinctive
  move for "slow". It keeps the empty balance and triggers another reconnect
  wave onto a throttled VM.
- **No alert on CPU balance or throttle.** The Sentry uptime monitor caught the
  symptom. Nothing warned that the balance was falling from ~50 s to 0 in the
  first minute.

## Action items

Each fix was PR'd into `fix/outage-fix-forward`, and everything shipped together
in #90 (release v238), so the trigger fired only once.

| Item | Outcome |
|---|---|
| Cut per-request auth cost. | **Shipped** (#88). One resolve per request; a 401 costs one scan instead of two. A 60 s in-process cache of successful resolutions, keyed by SHA-256, means a legacy token pays the O(N) scan once a minute: 0.003–0.008 CPU-s per cached request, down from ~1.7. Argon2 still runs on the event loop on a cache miss (follow-up). |
| Make cached resolutions revocable under concurrency. | **Shipped** (#89, #92), each after an adversarial security review failed the previous version. Eviction is per principal and unconditional (in a `finally`, never gated on `rowcount` or `commit()`, both of which the shared-connection race can corrupt), with a per-principal in-flight guard, so no caller can flush other users' cached tokens. The race harnesses show 0 leaks. |
| Pin `python:3.12-slim` by digest (u3, `sha256:78387bc3…`); no floating `apt` in the runtime image. | **Shipped** (#83). |
| Stop turning abandoned MCP requests into server faults. | **Shipped** (#86). A guard inside the MCP sub-app answers 499 when the client has gone, including when the SDK cancels a handler and returns nothing. It does not refund auth work an abandoned request already paid for. |
| Deploy workflow: test gate, `paths-ignore`, post-deploy observer with no auto-rollback. | **Shipped** (#84). First run: the observer could not read Fly metrics (HTTP 403 with the deploy token); follow-up. |
| Serialise the shared `sqlite3` connection. | **Reverted** (#87 → #93). Final verification found its lock made the event loop wait out the 5 s lock timeout behind a threadpool worker's open transaction: 10 s `/health` stalls and `database is locked` errors, none of which happen without it. The race predates this incident and did not cause it; it needs a redesign that never blocks the loop (follow-up). |
| Deploy-hygiene runbook. | **Shipped** (#85): `docs/runbooks/admin-operations.md` § "Deploy hygiene on Fly shared-cpu". |
| Legacy-token rotation, HMAC lookup, VM headroom, CPU alert, the 330 edge 301s, cheaper failed auth, the sqlite redesign. | `docs/FOLLOW-UPS.md` § "Reliability" |
